# BC Data AL compatibility and regression tests

`integration/Invoke-E12Permissions.ps1 -Target 'BC23 Baseline'` (or `'BC27.1'`) qualifies real UserPassword identities over the native HTTP/1.0 client. Run with PowerShell 7. It accepts only the two dedicated Test targets, derives temporary users/tenant roles from a random run ID, grants no I/M/D rights, and seeds only fixture tables. Test-only service `BCDCompatibilityE12` creates/cleans the fixture and fixed tenant roles using the existing administrator's rights, without a Permissions property. BC administration cmdlets create/remove the users and assign their tenant roles; no exposed Toolset operation implements these actions. Build/deploy/tests still use Toolset MCP.

The nine assertions cover denied parent/source reads, stored-field pagination without source-table access, read-only FlowField calculation, hidden headers/continuations, caller-filter intersection, inaccessible explicit filters and a source-filtered total of 10 versus administrator total 30. The harness retains credential-free evidence under `.bcdevtoolset/e12-<dedicated-container>-evidence.json`. Passwords travel only through process memory/private stdin, not configuration, state or command arguments. Cleanup in `finally` removes/verifies temporary users, tenant roles and both fixture tables. A retained metadata-only state file supports `-CleanupOnly` after interruption and refuses changed user/role ownership. The fixture service is never bundled. This harness tests HTTP/client behavior directly; it does not qualify restricted identities through the MCP configuration bridge or write/receipt semantics.

`integration/Invoke-E01Transport.ps1` runs direct HTTP assertions against only the configured `BC23 Baseline` and `BC27.1` dedicated Test targets. Run with PowerShell 7; it uses existing local UserPassword credentials without logging them and writes credential-free per-target evidence under `.bcdevtoolset`. Inspect `passed` and `failures`; failed action assertions also raise an error after writing evidence. Small Unicode/typed payloads and deliberate/malformed-JSON errors passed on both versions. The 65,568-byte request passed on BC23 but failed to return a complete response on BC27.1 under the configured 30-second limit. E01 remains open; the underlying connection failure does not establish an AL payload limit.

The instrumented reader `integration/E01Http.ps1` retains HTTP headers, partial body bytes, elapsed time and exception/cancellation details. `Test-E01Http.ps1` tests partial-body socket errors and timeout evidence entirely in memory. `Measure-E01Transport.ps1` and `Measure-E01Curl.ps1` retain repeatable, credential-free diagnostic evidence. The failure was isolated to ASP.NET Core 8 HTTP.sys unbuffered chunked-response writing in this environment, independently reproduced by `HttpSysControl`. Enabling kernel response buffering in that standalone control removed the failure; BC configuration was not changed. Container-loopback, gzip, and HTTP/1.0 comparisons succeeded. See the ledger for the limits of this diagnosis and the reproduction commands/code.

The dedicated container was recovered after the experiments. The full HTTP harness then passed with both `-Target 'BC27.1' -ResponseMode gzip` and `-Target 'BC27.1' -ResponseMode http10`. E12 adds four Restrictive tests in codeunit 50203 using Microsoft's BC23 Permissions Mock app. Each creates isolated AutoRollback data with test setup rights, then explicitly replaces those rights before calling the service. They check a stored-field read without related-table access, denied parent read, denied FlowField source read, and successful calculated read with read-only parent/source rights. Each also verifies its effective table permissions, and denials name the expected table. Test-only permission sets 50200-50203 grant no production rights and are not bundled. Company and Table Metadata reads are explicit baseline rights. The platform's permission mocks do not test security filters or a separately authenticated HTTP identity; E12 remains open for those checks and all mutation/receipt boundaries. See [Microsoft's permission-testing limitations](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-testing-with-permission-sets).

`integration/StoredCredentialQualification.ps1 -Action Setup` creates temporary configuration aliases for only the dedicated BC23/BC27.1 Test targets. It preserves existing stored credentials and, only when missing, creates a temporary stored copy of the target's configured credentials. The aliases contain wrong plaintext traps to prove stored reads do not fall back. Missing-credential aliases use random absent identities. Run actual MCP reads, then always execute `-Action Cleanup`; it removes aliases/test-created entries, preserves originals and retains credentials changed by the user during qualification. State under `.bcdevtoolset` contains cleanup metadata only. This is a development fixture, not credential migration or a production setup workflow.
